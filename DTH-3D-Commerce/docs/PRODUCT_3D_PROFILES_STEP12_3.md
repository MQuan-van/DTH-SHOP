# DTH Product 3D Profiles — Step 12.3

## Scope and integration

This step builds on the delivered Step 12.2 package. It affects the Product Detail viewer only.
The compatibility/price/cart domain is unchanged. Home, Story, loader and backend files are NOT updated.
The registry is a source-controlled local registry. This release does **not** add a MongoDB `threeD` field,
Admin upload/editor, hosting, asset transcoding, or any physical fitment inference.

The current Apex demonstrator gets a profile preserving the Step 12.2 default framing and three authored
notes. Other products keep automatic normalization; optional shaders still depend on their actual materials.
No new model is generated by this package. Source/license fields are declarations, not verified ownership.

## Data flow

Product ID + catalog modelUrl -> local profile candidate -> bounded GLB download -> GLB preflight
-> SHA-256 of exact bytes -> GLTF parse -> runtime geometry checks -> profile identity binding
-> normalized transform / camera / hotspots -> existing study shader + single camera controller.

Invalid metadata or an identity mismatch: original GLB can still be viewed with automatic framing,
without old annotations/transform presets. Unsafe/malformed/over-budget GLB: image fallback.

Profile fallback is not a fallback to demo *catalog* data. The API/Flow distinction is unchanged.

## Contract version 1

Authoritative validator: `shared/product3dProfile.mjs`. All fields required; nullable values explicitly allowed.

- schemaVersion: numeric 1.
- profileId, productId: bounded lowercase hyphenated IDs. One entry per product in the registry.
- version: semantic version of presentation settings, e.g. 1.0.0 (not the schema version).
- asset: unversioned `/models/...glb` URL and lowercase SHA-256 of the final GLB bytes.
- transform: rotation [x,y,z] in **radians, Euler XYZ**, positive uniform scale [0.5,1.5],
  offset [x,y,z] with each coordinate [-0.5,0.5] in normalized viewer units.
- camera: FOV 24..60 degrees; presets front/side/rear/detail, each position and target arrays.
- modes: surface/technical/hotspots strict booleans. Mode flags are permissions, not proof of support.
- hotspots: max 6 unique authored points with id, label, description, position, focus.
  `focus:null` uses safe default focus; an explicit focus is `{position:[...],target:[...]}`.
- provenance: source demo/photogrammetry/ai-generated/manual/unknown; tool, license, attribution,
  captureDate (real YYYY-MM-DD or null), optimized (boolean or null), purpose `visualization-only`.

Unknown fields, prototype keys, getters, nonfinite numbers, external/traversal model URLs, duplicates,
and out-of-range settings are rejected, not silently executed or coerced.

## Coordinate contract — important

There are two deliberate coordinate spaces, never millimetres inferred from an arbitrary model.

**Hotspot position**: exported asset-scene coordinates, including authored glTF node transforms,
but BEFORE this viewer's normalization. All parts share the exported scene frame, not a per-mesh origin.

**Camera position, camera target, transform offset**: normalized presentation coordinates.
The normalized sphere radius is initially 1.35. A camera reference pose is authored at 800x600
with its profile FOV; on narrow viewports the controller increases distance to keep the model framed.
The current zoom ratio is preserved during resize. Static catalog fitment never reads these coordinates.

Transform chain:

    source point -> subtract original bounding centre -> multiply by (1.35/sourceRadius)*scale
                 -> Euler XYZ rotation -> add presentation offset

Exactly the same matrix is used for the displayed object, hotspot positions and scan-height range.
Source vertex buffers, authored node transforms and maps are not rewritten. `scale` changes normalized
scene size; automatic camera distance also adapts. Use camera presets to tune composition, not repeated
CSS/GLB scale patches. An unsafe camera or outside hotspot invalidates the custom presentation and
falls back to safe automatic framing.

All camera paths orbit around an interpolated look-at target. Radius is bounded outside the model sphere.
Reset uses the profile's Front view and the existing UI clears study/light/hotspot state.
Motion off settles commands; blocked/hidden viewing cancels pending movement through the existing gates.

## Register a new asset later (no scan required now)

1. Export a static, self-contained GLB. Optimize before publication. This pipeline supports ordinary
   GLB and EXT_meshopt_compression; Draco and KTX2 need a separate decoder integration and are rejected.
2. Put it under `frontend/public/models/products/your-part-v1.glb`.
3. In CMD at DTH-3D-Commerce, run:

```bat
node tools/inspect-product-asset.mjs --file "frontend/public/models/products/your-part-v1.glb" --product "your-product-id" --url "/models/products/your-part-v1.glb" --out "frontend/src/shop/product/3d/profiles/your-part.profile.json"
```

This reads the file, enforces preflight budgets, prints its exact SHA/metrics, and creates a template.
It does NOT infer hotspots, physical dimensions, source/rights, or compatibility. It refuses to overwrite
an existing output file. `--out` omitted = report only, no file changes.

4. Review the template. Use `source:'ai-generated'` for generative image-to-3D output, not 'photogrammetry'
   just because the input was a photograph. Fill license/source accurately; unknown is allowed.
   Leave hotspots disabled until their coordinates/description have actually been authored.
5. Import the JSON as data in `frontend/src/shop/product/3d/assetProfiles.mjs`:

```js
import myPart from './profiles/your-part.profile.json' with { type: 'json' };
// Add to the EXISTING array; do not duplicate a productId.
export const PRODUCT_3D_PROFILES = Object.freeze([APEX_PRODUCT_3D_PROFILE, myPart]);
```

6. Set that product's catalog modelUrl to exactly `/models/products/your-part-v1.glb` via the current
   product data workflow. Registering a profile does NOT change the product's catalog URL or fitment.
7. Test the product in 3D: Front/Side/Rear/Detail, Surface/Technical, resize, Motion off, Image/Retry.
   Add hotspots only for this final asset; any changed GLB requires a new hash and marker review.
8. Use a new versioned asset path for a new model revision; avoid overwriting a published immutable file.
   The request also has `?v=<sha256>`. A 2-entry raw-byte session cache is bounded and clearable by Retry.
   Browser/HTTP caching cannot detect a file changed in place until it is revalidated or fetched anew.

Do not enable a profile by replacing SHA with a wildcard. A hash match binds metadata to bytes;
it does not establish origin, copyright ownership, CAD accuracy or fitment.

## Product budgets and supported data

Preflight: <=16 MiB GLB, <=2 MiB JSON, <=96 MiB declared decoded buffers,
<=1,000,000 vertex records, <=500,000 triangles, <=256 meshes, <=2048 nodes,
<=128 materials, <=16 embedded images, <=4096px on an edge and <=33,554,432 decoded pixels
(32*1024*1024 in code). Runtime also checks finite vertices, triangle indices and transforms.

A smaller budget still applies to optional Technical shaders from Step 12.2 (120,000 triangles,
240,000 vertices, 80 meshes and compatible PBR materials). A profile cannot force unsupported shaders on.

Rejects external/data-URI dependencies, animated/skinned/instanced/morphed assets and sparse accessors
in this V1 static product pipeline. Image formats: embedded PNG, JPEG, WebP. Decoder errors still fall
back to the product image. Preflight reads dimensions before texture decoding; it is not an exhaustive
image validator or a full glTF conformance/security certification.

## Not implemented here

No Admin profile UI/import upload, automatic hotspot placement, new payment/order logic,
physical size calibration, model repair/remeshing/transcoding, or model-based fitment decisions.
A source-controlled data contract is the prerequisite for an Admin editor later, not that editor itself.
